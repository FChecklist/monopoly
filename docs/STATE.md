Fixed at the root:
VERIFIED CLOUDFLARE LIMITS (read from the current documentation on 19 Nov 2026): Workers limits, https://developers.cloudflare.com/workers/platform/limits/ : subrequests per invocation 50 on Free, 10,000 on Paid (calls to Cloudflare services such as D1 count as subrequests); simultaneous open connections 6; CPU time 10 ms per HTTP request on Free (network waiting does not count), 30 s default and 5 min maximum on Paid. D1 limits, https://developers.cloudflare.com/d1/platform/limits/ : queries per Worker invocation 50 on Free, 1,000 on Paid; ONE db.batch() COUNTS AS ONE QUERY (a batch of 2,000 statements runs in one invocation, 2,000 separate queries fail with "Too many API requests by single Worker invocation"); 100 bound parameters per query; 100 KB per SQL statement. We deploy Free only. Our counter treats a D1 query and a provider HTTP call as one unit each (the stricter reading of the two limits).
(1) READ SIDE IS SET-BASED. The port has db.reads(stmts): several SELECTs in ONE batch (local: a loop, D1: d1.batch, counted as ONE). settleBounded reads the schedule (targets, tiers, where each history starts, streaks, the saved cursor) in ONE call, then up to 12 units (one period of one target, or the streak run of a target) per call: events, rewards and marks of EVERY member of those units in the same batch. Team units read the team list, the stored snapshot members, the events, the rewards and the marks in the same batch; a team snapshot is written once, at the first close of a period (about 4 calls per team, one time). Streak units read the hit sets of every period of the target as one statement per period inside ONE batch (a batch of hundreds of statements is still one call). So the read cost of a settle turn does not depend on the number of members, teams or targets: measured, a settled turn costs the same for 2 members and 40 members (test A2), and a unit that did not change costs nothing of its own. The overview reads its thirty numbers through coalescingDb (all SELECTs started in one round go in one batch): a handful of calls instead of 34 to 47.
(2) WRITE SIDE. Deciding is done in memory from those rows; only a member whose fingerprint differs from the mark of its last CLEAN visit is settled. A first payment is inherently one provider call plus the guarded money path: measured 18 calls (22 the first time a person gets a provider account), of which 1 is the provider request and 1 the mark; the first-time-payment path skips the reads that would only confirm "nothing there" (settleEntitlement fresh hint: still the same guarded INSERT and the same idempotency key, so it can never pay twice). The mark is written in the same statement that reads the group (the database computes the fingerprint), so there is no extra read. The auditor's target of "about 6 calls per first visit regardless of N" cannot hold for the PAYING part (every payment is its own provider call and its own guarded write): what is independent of N is everything else.
(3) NO HEAD-OF-LINE BLOCKING. A member whose visit did not finish cleanly (an error, a skipped reversal, a busy group, a block in force) gets a RETRY mark (retried after 2 minutes; a block in force after 6 hours) and the loop goes on to the next member and unit; the cursor passes every unit that is done. A visit that is cut by the budget leaves the member for the next turn (nothing is marked). When even one visit cannot fit the budget (TICK_QUERY_BUDGET below about 32) the overview shows the alert budget_too_small ("one visit needs N calls, the budget is M"), and the signed tick route (the driver) runs with a one-off allowance of 32 anyway: it is never silent. (4) MARKS ONLY ON CLEAN VISITS: no mark is written after a swallowed error, a skip, a busy or stale group; the test cuts a first visit with an error at each of 30 query positions: the group is paid within a few ticks, once. (5) STREAKS HAVE THEIR OWN UNIT: no dependence on a tier settle in the same tick (test A6: tiers settled first, a streak added later pays without any tier change). (6) ERROR STATE PER STAGE: table tick_stage (stage, first_at, last_at, count, ok_at), cleared only when THAT stage runs cleanly; the overview lists every flagged stage; last_tick_ok_at is stamped only when no stage is flagged AND both turns (core, settle) ran cleanly within 45 minutes. (7) LAZY TICK: every request is counted as one invocation (the db and provider ports are wrapped in handle()); a signed-in request starts a tiny tick only if it has used 12 calls or fewer, with its own budget of 20 (light stages and at most a row or two of sending, never the settle), reduced by what the request already used; it never stamps the clock. Measured: the overview as the first request of a window stays under 30 calls, the overview alone about 10. Consequence, stated in DEPLOY.md: on the free plan a deploy NEEDS the driver (scripts/tick.js from a scheduled workflow, or a Cloudflare Cron Trigger Worker) for period bonuses and streaks; without it the overview shows the tick_stale alert. (8) CORE FAIRNESS: the core stages start at a different one every cycle and each has a minimum share (sent 14, released 5, resumed 3, reversals 5, penalties 5, orders 4, AI 3 and 2); sendReward checks the budget BEFORE it counts an attempt, and an attempt is taken back if the budget cut came before the credit call, so a budget cut is never an attempt (test A9). BudgetReached is no longer swallowed by retryQueued. (9) The admin settle and the season close are bounded: they answer { more: true } until done (the season is closed only when nothing is left); the cursor is shared with the clock. (10) The range queries use the index: group_key >= prefix AND group_key < prefix with the last character raised (EXPLAIN-checked in test A12), never LIKE.

ROUND 25 (INVARIANTS UNDER CONCURRENCY): the lazy tick, the cron tick, the signed ingest tick, the admin settle and a season close can all run settleEntitlement for one group at the same time and nothing locks them. So the database, not key luck, enforces it: (1) the cash grant of a period entitlement is a guarded INSERT that holds only while the group's COUNTED total (queued, sent, waiting and recorded rows, including delta and net rows) is still the figure it was computed from (paidGuard in grant()); a stale run inserts nothing and answers 'stale'; (2) the net row (reward.net) carries the same guard and the correction equality guard; (3) settleEntitlement is a bounded loop (6 tries, small back-off) around settleOnce: on 'stale' it reads the group again and recomputes, and after the bound it skips the group for this run (skipCode busy), never paying from an old figure; (4) netCorrections reads the group's counted total itself, so a net is never larger than entitled minus counted, and a busy audit chain or a lost race while netting aborts that group for this run (it never falls through to a cash payment). Invariant: counted gross paid for the group - recovered corrections <= entitlement, for any interleaving. Also: the re-issue amount key present but null is 400 bad_amount (absent = the whole rest); the ledger look-up for a duplicate_unconfirmed reads up to 20 pages of 100 lines (bounded; a credit older than that is not found and the admin checks the ledger by hand).

Re-issue details: it is ONE batch (close of the old row and insert of the new one; the close carries the same budget guards as the insert, so the old row is never closed without the new one); its audit line is that batch's own reward.create with the admin as actor and reissue_of; asked again after it worked it answers 200 replay:true for the same amount, 409 changed for another; a new amount above 500 is refused; the note must be a string of at least 10 characters. Erasing a person scrubs the account and any admin note from the notes of their reward rows (amounts, ids, states and a maybe_landed marker stay; the reseal has nothing to bring back).
